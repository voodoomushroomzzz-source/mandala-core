# Пакетное сохранение контекста внешних ассистентов

Обновлено 19 ноября 2026 года. Источник — прямое решение Садовника.

## Область применения

Общее правило для всех **внешних ассистентов Мандалы**, работающих из диалогового чата через подключённые GitHub, Notion, Google Drive и другие доступные инструменты. Включает Мандалу, Личного, Куртош Менеджера и новые внешние направления независимо от устройства Садовника.

Это правило **не относится к локальным ассистентам**, работающим с локальной копией репозитория и реализацией. Они следуют [локальному рабочему порядку](local_sr_workflow.md) и инструкциям своих модулей. Среда и маршрут определяют применимость, а не имя ассистента, не наличие телефона или ПК у Садовника.

## Накопление

Не перечитывай и не перезаписывай файлы после каждого небольшого уточнения. Накапливай связанные изменения в доступном контексте текущего диалога. Повторные уточнения одной записи объединяй в последнее согласованное состояние, сохраняя значимые причины и историю решения там, где она нужна.

Различай факты со слов Садовника, подтверждённые решения, предварительные оценки, гипотезы и предложения ассистента. Не превращай свободный разговор в автоматически принятые задачи или сроки.

## Когда сохранять пакет

- По прямой команде Садовника применить или сохранить накопленное.
- Самостоятельно после содержательного этапа, когда связанных изменений достаточно, нужна передача другому чату или возникает риск утраты важного контекста.
- Явную просьбу сохранить конкретную задачу, решение или дедлайн выполняй своевременно; не откладывай её автоматически ради большого пакета.
- Если операция требует отдельного согласия по рабочему маршруту, накопление не заменяет это согласие. Не расширяй имеющийся объём полномочий.

Дополнительное подтверждение обычной записи не требуется, когда она уже разрешена прямым запросом или действующим согласием. Новые приоритеты, сроки, выход из паузы и внешние публикации должны опираться на явно согласованное содержание.

## Как сохранять

1. Перед записью перечитай только затронутые актуальные исходники и применимые правила модулей по [корневому README](../../../README.md#module-readmes). Не перечитывай весь контекст без причины.
2. Сохрани параллельные правки и чужие записи. При изменении исходника заново сопоставь накопленное с его актуальным состоянием.
3. Записывай связанный пакет одним коммитом, если доступно атомарное изменение нескольких файлов. Не создавай отдельный коммит на каждую реплику без необходимости.
4. Проверь синтаксис и корректность исходных данных и ссылок. Успешное сохранение определяй по результату операции записи. Для обычных изменений данных применяй раздел «Проверка страниц и сборок» ниже; при изменении кода, представления или сборки следуй проверкам затронутого модуля.
5. Дай одну краткую сводку: что сохранено, что не завершено и где продолжить.

До успешной записи говори «учёл для общей записи», а не «сохранил». Контекст чата не является долговечной памятью и не означает фоновую работу. Перед передачей другому чату сохрани значимую точку продолжения в разрешённом объёме. При сбое честно укажи несохранённое; не утверждай, что оно переживёт завершение чата.

## Проверка страниц и сборок

По прямому решению Садовника от 19 ноября 2026 года после обычного создания или изменения задачи, контекста, карточки либо другого исходного материала внешний ассистент сохраняет данные и даёт ссылку на результат. Не нужно каждый раз открывать страницу задачи или дашборд, опрашивать GitHub Actions, ждать пересборки/публикации и проверять производные HTML или граф только ради подтверждения отображения записи.

Это правило действует для всех внешних диалоговых ассистентов и имеет приоритет над общими требованиями модулей проверять страницы после каждой записи данных. Успех сохранения исходника не является подтверждением обновления страницы: без отдельной проверки не утверждай, что страница уже обновилась, всё отображается или сборка прошла успешно. Ссылку можно дать сразу после успешного сохранения.

Проверки страницы и сборки выполняются по явному запросу Садовника, при сообщённой или уже обнаруженной ошибке, а также когда сама задача меняет код, представление, генератор, workflow или механизм публикации. Проверки корректности исходных данных и сохранения, а также специальные проверки реально выполняемой операции в другом сервисе этим не отменяются. Локальный инженерный цикл остаётся прежним.

## Куртош: два разных буфера

Накопление диалоговых уточнений до записи в GitHub и [буфер переноса в Notion](../../personal/kurtoch/notion_change_buffer.json) — разные этапы.

- При сохранении пакета рабочих данных на GitHub одновременно обновляй соответствующие записи notion_change_buffer.json по [инструкции менеджера](../../personal/kurtoch/mobile_manager_onboarding.md).
- Если есть прямой запрос создать или изменить рабочую задачу, запись исходника и буфера не откладывай без причины.
- Повторные правки записи объединяй по действующей схеме буфера.
- Общая политика пакетного сохранения **не даёт разрешения автоматически выгружать в Notion**. Состав и версии переноса согласуются по инструкции менеджера; после применения проверяется результат и только затем очищаются выполненные записи.

## Проверочные сценарии

- Несколько внешних уточнений одного направления → накопление без записи после каждой реплики → один пакет после этапа или команды.
- Прямой запрос сохранить дедлайн → своевременная запись, а не потеря в ожидании пакета.
- Внешний Куртош → пакет GitHub + буфер → отдельное согласие на Notion → проверка и очистка выполненного.
- Локальный ассистент с тем же именем → этот документ не меняет его рабочий цикл.
